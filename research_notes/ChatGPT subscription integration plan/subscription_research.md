# Official ChatGPT subscription integration

## What supported subscription access exists today?

### Takeaway
As researched on 2026-10-24, OpenAI documents a direct Sign in with ChatGPT (SIWC) path for eligible local open-source/personal tools. The project should modernize its existing native subscription path rather than create another provider or import another product's credentials.

### Cited Findings
- The September 28, 2026 cookbook distinguishes verified identity from optional ChatGPT plan inference permission. Eligible Plus and Pro subscribers can authorize plan usage without API keys. Local open-source and personal tools are supported; paid or remotely hosted distribution requires requesting access. This grants neither ChatGPT conversation access nor other account context. The example DevKit contains `@siwc/local` and React components, but its license must be checked before reuse. The documented example is Electron, not a claim of tested Bun support. — [OpenAI cookbook](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt)
- An OAuth client registration belongs to one authenticated user and selected workspace. A host identifies an installation/runtime; restarting or changing accounts does not create a new host. Persist a stable opaque host identifier, for example `urn:uuid:<UUIDv4>`. A client can be reused across hosts for that same user/workspace, but hosts have distinct IDs. Host IDs are identifiers, not credentials or proof of possession. — [SIWC overview](https://developers.openai.com/siwc/token-sharing-open-source)
- The public subscription inference route is `POST https://api.openai.com/v1/responses` using the authorized OAuth access token as a Bearer credential. OpenAI explicitly says not to use ChatGPT `backend-api`. For discovery, `GET https://api.openai.com/v1/models` with that same credential returns a `models` array, not necessarily the usual API-key catalog shape. Filter `visibility == "list"`, show `display_name`, send `slug`, and retain server order. Refresh the catalog on account switches. Only a successful `response.completed` confirms inference; discovery or connected identity alone does not. A stream can fail after partial text. — [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)

### Inferences
- This is a direct, app-owned integration opportunity, not a need to emulate the Codex CLI or replace the existing query/tool loop.
- A project advertised as personal/local use can target this route first. Enabling a shared, paid RCS service for arbitrary users is a separate distribution/access decision.
- An ordinary API key and subscription-authorized OAuth grant are different credential/billing modes. Choosing subscription mode must never silently fall back to API-key billing.

### Gaps
- No account was authenticated, no live entitlement was checked, and no subscription quota was consumed in this planning work.
- The documentation does not establish this user's exact account eligibility, regional admission, workspace policy, or available models. These need a real authorized smoke test.
- The fetched documentation does not establish a stable, published Bun-compatible `@siwc/local` package contract. Treat the DevKit as reference implementation until license, packaging, maintained release, and Bun behavior are checked.

## What authentication, state, and request contracts must the plan implement?

### Takeaway
Use app-owned dynamic registration with explicit plan consent, protected profile storage, public Responses streaming, and full client-maintained context. Existing app tool execution remains local and retains its permissions.

### Cited Findings
- First registration uses `client_id=dynamic_agent_client`, consistent actual-app `agent_name_hint`, and persistent `ext_agent_host_id`; retain the issued callback client ID for exchange/reauthorization. Authorize at `https://auth.openai.com/api/accounts/authorize`; use loopback `127.0.0.1`, fresh state/nonce and PKCE S256. Keep callback scheme/host/path stable; only its port can change. Request `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`, resource `https://api.openai.com/v1`. Validate callback state/errors/client association. Exchange form data at `https://auth.openai.com/api/accounts/oauth/token` with issued client ID, code, verifier, exact redirect and resource. Verify ID-token signature/JWKS, issuer, audience, expiration, nonce, and returning subject before activation. Check token-response granted scopes; identity alone is insufficient. Store profiles separately per client and validated identity. Write tokens atomically and protect local files. — [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)
- Refresh near expiry using form `grant_type=refresh_token`, saved issued `client_id`, latest `refresh_token`, and resource at the above token endpoint; omit scope to retain the grant. Serialize refresh across processes. Keep registrations distinct even when emails match, and retain mapping/host ID after logout. Revoke a renewable session using the discovery document's revocation endpoint, form token, refresh-token hint, and issued client ID; clear local tokens afterward. If local logout finishes without confirmed remote revocation, disclose that fact. Never log tokens or authorization URLs containing `id_token_hint`. For Plus, the documented five-hour total is shared across all apps; the same five-hour limit does not apply to Pro. Link to ChatGPT Settings > Usage rather than guessing remaining allowance. — [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)
- Access tokens currently last one hour; refresh tokens last 30 days and rotate to a fresh 30-day token on successful refresh. The token response includes expiry/grant metadata and `earliest_refresh_at`. Persist actual returned data rather than infer refresh state only from an unverified JWT payload. — [Token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference)
- HTTP subscription requests require `store:false`, `stream:true`, array input containing needed history, and `instructions` or developer content rather than explicit system items. Omit `previous_response_id` over HTTP. Unsupported request fields include background/conversation, max output/tool counts, metadata/moderation/multi-agent, prompt and prompt-cache retention, safety identifier, temperature/top-p/top-logprobs, truncation and user. Group function/custom tools into namespaces or use `additional_tools` items. Hosted image generation, file search, Code Interpreter, native computer use, hosted MCP/connectors, and Responses `tool_search` are unavailable; programmatic tool calling is not accepted in top-level tools. Model-supported text/image/file inputs are allowed; audio/video, upload API, and transcription are not. Codex can execute local tools via functions, but this does not enable unavailable hosted tool types. — [Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)
- Namespace schema uses `type:"namespace"`, a name/description, and nested function tool definitions; existing JSON-schema functions can be grouped without replacing application execution. Explicit `strict:false` retains best-effort schemas when the existing schema does not meet strict requirements. Tool definitions do not grant execution permission. — [Function calling](https://developers.openai.com/api/docs/guides/function-calling)
- Stateless Responses output includes opaque encrypted reasoning items; preserve output items and replay them with function calls and outputs across subsequent requests. Visible assistant text alone does not preserve reasoning continuity. Current documentation says encrypted reasoning is returned by default with `store:false`; the older explicit include remains compatible. — [Reasoning models](https://developers.openai.com/api/docs/guides/reasoning)
- Only completed inference is success; separately handle incomplete/error/interrupted terminal states. Preserve HTTP status, error code/parameter, body shape, and request ID. Before a stream, admission can return a `detail` body rather than the usual error envelope. Missing plan permission disables inference. Eligibility and unsupported-capability/route errors should not be retried unchanged; usage limits pause new subscription requests. Temporary availability errors retain credentials and use bounded backoff. Terminal refresh failure clears unusable tokens and restarts OAuth with retained issued client ID; temporary failures must not delete credentials. Disconnection has no push notification. — [Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery)
- App-server also supports app-owned SIWC tokens, with a Responses provider and token supplied privately to its child environment. Renewing tokens requires restarting that configured process and resuming its saved thread. Initialize client attribution consistently. Its model RPC may be a bundled catalog, not entitlement verification. — [Codex app-server](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

### Inferences
- MVP should maintain an allowlisted request shape specific to subscription mode, not forward every generic Anthropic/OpenAI option.
- Namespaced tool conversion needs matching request/replay/demultiplexing tests; do not assume tool names are unchanged in all returned event shapes.
- Keep opaque Responses output metadata separate from visible messages and tied to session/turn identity. Never reconstruct encrypted reasoning from displayed thinking text. Existing session storage must preserve it through resume, tool rounds, and compaction decisions.
- Prefer installed OpenAI SDK stream parsing if it fully supports the subscription request shape. A new auth dependency is justified only if no installed JOSE/OIDC implementation handles JWKS verification safely; hand-decoding JWT is not validation.
- A successful smoke test must cover a second request after a local function result, not only text generation, because this is a coding harness.

### Gaps
- Exact model-specific reasoning levels, service tiers, supported file representations and namespace return behavior must be validated against selected account models; do not hardcode a catalog from generic documentation examples.
- API input history growth/compaction and privacy requirements depend on the project's persistence design; code researcher owns those details.

## How does the current implementation differ, and what should change first?

### Takeaway
The repository already has subscription login and a Responses bridge, but its authentication and inference are based on a Codex-specific route. Reuse that branch while migrating its ownership and wire contract; a URL-only patch is insufficient.

### Cited Findings
- `src/services/api/openai/chatgptAuth.ts:7` hardcodes a Codex-style public client ID. `:197` starts device authorization and `:277` exchanges at `/oauth/token`, whereas `:300` refreshes under that fixed client and connector scopes. No app-issued SIWC client ID, stable host ID, direct plan scope or verified identity record is persisted. Compare with the requirements above. — [Local auth source](../../src/services/api/openai/chatgptAuth.ts), [SIWC registration](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)
- `chatgptAuth.ts:52` constructs a Codex credential fallback path; `:342` automatically reads that file when app-local auth is absent. A borrowed registration's refresh credentials can be rotated and then saved into the application's separate file at `:355`. That creates an inferred ownership/rotation conflict if the original Codex process continues using its old token. No personal credential files were opened in this research. — [Local auth source](../../src/services/api/openai/chatgptAuth.ts), [Refresh serialization requirement](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)
- `chatgptAuth.ts:74` decodes JWT payloads without signature/JWKS validation. `:148` writes the token file directly, without atomic replacement. `:330` logout removes only the app's local file and has no remote revocation or disabled fallback state. — [Local auth source](../../src/services/api/openai/chatgptAuth.ts)
- `src/services/api/openai/responsesAdapter.ts:491` calls `https://chatgpt.com/backend-api/codex/responses` and `:483` supplies ChatGPT Origin/Referer headers. The documented direct flow explicitly excludes that backend. This is the primary interoperability mismatch, regardless of whether the existing path sometimes works. — [Local adapter](../../src/services/api/openai/responsesAdapter.ts), [Supported inference route](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)
- Existing adapter already sets stream true/store false, builds array history, extracts system/developer text to instructions, converts tool calls and results, and reports normalized usage. Its flat function list (`:138`) needs subscription-compatible namespacing. Its converters rebuild visible text/functions and do not retain opaque reasoning outputs. — [Local adapter](../../src/services/api/openai/responsesAdapter.ts), [Preview contract](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations), [Reasoning replay](https://developers.openai.com/api/docs/guides/reasoning)
- `responsesAdapter.ts:445` shares one success-emission branch for completed/incomplete; EOF without a completed event does not explicitly fail. Errors at `:439` keep only error message, losing typed code/status/request-ID handling. SSE framing splits only on `\n\n`, so CRLF frames and reader cleanup/cancellation deserve coverage if this parser is retained. — [Local adapter](../../src/services/api/openai/responsesAdapter.ts)
- Root `package.json:181` already declares OpenAI SDK `^6.34.0`; model-provider workspace has another OpenAI SDK dependency at `packages/@ant/model-provider/package.json:16`. No new inference SDK is inherently necessary. — [Root manifest](../../package.json), [Provider manifest](../../packages/@ant/model-provider/package.json)

### Inferences
- Recommendation: preserve existing `OPENAI_AUTH_MODE=chatgpt` native route and application tools/permissions; replace its app authentication and migrate the existing Responses adapter to official SIWC contract. Do not install a second agent runtime solely for subscription billing.
- First implementation gate: authenticate one owned SIWC profile and complete one public Responses call using its direct permission. If the real account is ineligible or direct admission unavailable, surface that limitation before building broad UX. A supported Codex app-server execution mode is a distinct alternative, not a credential fallback.
- Phases after gate: (1) secure profile/host/auth lifecycle and migration/re-login, (2) public stream/tool/history bridge, (3) catalog/capability/billing-status UX, (4) auth-concurrency, permission, replay, error, and existing API-key regression tests. All scope should be tied to existing callers identified by code researcher.
- Existing Codex tokens must not simply be relabeled as SIWC. Require fresh app consent; preserve legacy files for a reviewable migration and never alter Codex-owned credentials.
- Retain token counts as measurements; show plan-backed billing rather than inventing a per-request subscription dollar cost or quota percentage.

### Gaps
- This was static review plus official documentation research. No test suite, CLI login, remote service, paid inference, or secret inspection was performed.
- Native authentication support for remote/headless environments requires a separate supported UX decision; the documented OSS SIWC flow is browser/loopback, not permission to reuse the old Codex device client.
- Windows credential ACL behavior and cross-process lock primitives must be selected from the project's existing storage helpers; Unix mode bits alone are not evidence of equivalent Windows isolation.
